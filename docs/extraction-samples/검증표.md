# 추출 정확도 검증

> `docs/extraction-samples/검증표.md`
> `./scripts/verify-extraction.sh ~/Desktop/samples/*.png` 실행 후 화면과 대조하며 채운다.
> 원본 응답은 같은 폴더의 `<파일명>.json`에 있다.

## 무엇을 모을 것인가

같은 화면을 반복하지 말고 **성격이 다른 것**을 모은다. 반복은 이미 통과한 경로를 다시 밟을 뿐이다.

- [ O ] 요약 화면 (구간표 없음)
- [ O ] 1km 자동 분할이 보이는 화면
- [ O ] 랩이 있는 화면 (인터벌 훈련)
- [ O ] 구간이 20개 이상인 긴 기록
- [ O ] 다른 앱 (NRC / 삼성헬스 / Strava / 애플 피트니스 등 두 종류 이상)
- [ O ] 날짜에 연도가 없는 화면
- [ - ] 숫자가 잘리거나 흐린 화면
- [ - ] 마일 단위 화면 (있다면)

## 기록표

한 샘플당 두 줄이다. **화면 줄만 직접 적는다.** 추출 줄은 스크립트 출력이나
`docs/extraction-samples/<파일명>.json`에서 옮긴다.

## 특히 볼 것

**없는 값을 지어내지 않는가** — 가장 위험하다. 화면에 칼로리가 없는데 그럴듯한 숫자가 들어오면 사용자가 검토 화면에서 알아채기 어렵다. `null`이 와야 할 자리에 숫자가 있으면 즉시 기록한다.

**단위 변환** — `10.24 km` → `10240`, `52:31` → `3151`. 소수점이나 자릿수가 밀리지 않는지.

**날짜** — 연도가 없는 표기에서 엉뚱한 해로 가지 않는지. 오전/오후 구분이 맞는지.

**구간 종류** — `labelText`를 보고 split/lap을 맞게 골랐는지. `unknown`이 나오는 건 실패가 아니다. 억지로 고르는 것보다 낫다.

**구간 값이 누적인지** — 라벨이 `1km, 2km, 3km`인 화면에서 `distanceMeters`가 `1000, 1000, 1000`으로 오는지, `1000, 2000, 3000`으로 오는지. 후자여도 `normalizeSegments`가 잡아주지만, 프롬프트가 먼저 처리하는 편이 낫다.

**안정성** — 502가 몇 번 나는지. `stop_reason`이 찍히면 어떤 이미지였는지 함께 적는다.

## 판단 기준

| 결과 | 다음 행동 |
| --- | --- |
| 거리·시간이 8/10 이상 정확 | 통과. 앱 쪽으로 진행 |
| 특정 앱에서만 실패 | 그 앱 화면의 특징을 시스템 프롬프트에 명시 |
| 없는 값을 지어냄 | 프롬프트에 그 상황을 구체적으로 적어 교정 |
| 구간표만 계속 틀림 | 요약 화면만 지원하는 범위 축소도 선택지 |
| 502가 반복 | `stop_reason`별로 대응 (max_tokens면 상한 인상) |

거리와 시간이 핵심이다. 이 둘이 맞으면 나머지는 검토 화면에서 사용자가 고칠 수 있다. **완벽을 목표로 하지 않는다.** 손으로 입력하는 것보다 빠르면 이 기능은 성공이다.
